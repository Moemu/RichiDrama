# 生成任务与创作编辑闭环改进计划

日期：2026-08-19  
基线：`origin/main` @ `191f0e3`

## 目标与不变量

本轮的目标是让生成任务、积分预授权、项目/分镜删除以及前端编辑状态形成可恢复、可取消、可告知的闭环。任何用户可见的“生成中”都必须具有以下之一：可轮询的任务 ID、可用的手动刷新入口、明确的失败/未知状态，或明确不可取消的厂商在途说明。任何终止的本地任务都不得继续持有可释放的预授权。

## 已在主线验证的修复

1. 服务重启将“尚未提交厂商”的视频任务标记为 `retryable` 时，会释放旧的 `billing_authorization_id`，避免用户重试重复冻结。
2. 删除有活跃 `video_generations` 的项目会被阻止，避免软删除后继续消耗厂商成本。
3. `POST /api/v1/omni-video-jobs/:id/cancel` 已存在：未提交厂商的任务可取消并释放预授权；已提交任务会明确拒绝伪取消。
4. 任务轮询耗尽后会写入 `unknown`，并在自由创作页提供手动刷新。
5. 素材库删除后会回退页码重载；加载失败会保留旧数据并提示错误。

## 仍需修复的缺口

### P0：取消路径必须覆盖所有入口

- 现有取消 API 只覆盖全能视频任务。项目删除采取“阻止删除”策略，因此 UI 必须在项目/分镜生成记录中提供可发现的取消入口；不能只让用户到另一个页面寻找任务。
- 分镜删除也必须采用相同的保护：`sd2_waiting`、生成、持久化、超分与插帧阶段都不能被软删除成无入口的孤儿任务。
- `generationTaskStore.cancelTask()` 当前调用通用 `taskAPI.cancel`，而全能视频任务取消要求 `omniVideoAPI.cancelJob`。需要以任务元数据区分，失败时不得把本地任务直接伪标记为已取消。
- 所有取消/重试必须刷新分镜与历史记录，防止旧 `processing` 状态在左侧列表滞留。

### P1：删除引用与并发编辑

- 删除素材前查询分镜和全能镜头对该素材的引用；若被引用则返回冲突与引用清单，客户端提示用户先替换/解除引用，禁止静默持久化“丢失的素材”。
- 分镜更新必须带版本（以 `updated_at` 为乐观锁令牌）。服务端 `UPDATE` 必须以旧版本为条件；冲突时返回 409 语义错误和最新版本，客户端提示刷新而不是静默覆盖。
- 全能镜头更新同样使用 `updated_at` 条件，解决 FilmCreate/FreeCreate 双编辑面互相覆盖。

### P2：失败必须可见且可恢复

- 自动保存的定时回调不得吞错。失败后保留草稿、显示一次错误，并允许后续编辑重新触发保存。
- 历史加载失败不能置空已加载历史；应保留旧值并展示可重试错误。
- 后端重试路由、未知状态查询及待对账状态必须从统一状态常量派生；待对账应在用户端显示“处理中止，等待管理员核对”的解释和刷新入口，不能表现为无按钮死状态。

### P3：其余已报告体验问题

- 账户中心的初始加载/刷新失败显示可读错误且保留上一次内容。
- 重命名仅在服务端成功后更新本地名称；失败时恢复输入值并报错。
- 批量上传按成功/失败计数汇总，不得将部分失败报为“全部完成”。

### P3：上传、计费与素材操作反馈

- 上传先读取服务端 `/upload-limits` 并在客户端按媒体类型和大小预检；保留失败的 `File` 对象，展示逐文件进度和“重新上传失败项”。
- 请求预览通过现有 `/billing/quotes` 读取当前模型与时长的预估冻结积分，明确最终按供应商真实用量结算；历史版本显示结算后的实际积分，未结算时显示待结算。
- 小屏设备将“拼接视频”和“批量操作”两个悬浮栏错开，避免互相遮挡；视频裁切在提交前展示目标片段和原片时长。

## 实施顺序

1. 在路由与服务层补齐引用保护、乐观锁及取消语义，并为每个错误分支添加 Node 测试。
2. 将前端 API 请求附加版本，处理冲突、取消与未知/待对账状态；消除关键保存与加载的静默 catch。
3. 补充前端结构/行为测试，运行两端测试与前端生产构建。

## 非目标与边界

不会在脚本或前端直接调用供应商 API。所有真实生成、取消和计费状态都通过项目 `/api/v1` 路由及其鉴权、计费链路执行。
