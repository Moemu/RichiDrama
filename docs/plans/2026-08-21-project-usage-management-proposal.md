# 项目用量管理改造方案（审核稿）

日期：2026-08-21  
状态：待产品审核；本文不包含数据写入、回填或线上变更。

## 1. 目标与结论

将运营后台当前“模型用量”从以单条账本为中心的审计页，升级为以**项目**为中心的“项目用量管理”。分类和信息层级对齐 OEM 后台的项目管理方式：

1. 项目列表负责检索、概览、状态判断和排序；
2. 项目详情负责逐层钻取；
3. 明细账本仍保留为可审计的末级证据，不再承担项目概览职责；
4. 所有金额仍以既有 `billing_usage_logs` 和预授权/结算账本为准，不重新计算历史消费。

这不是把 OEM 的“完成度、剧集、角色、场景、道具”原样搬入运营后台。短剧平台项目用量管理的主问题是成本与任务归属，故采用相同的“列表 → 详情 → 子对象”结构，但子对象替换为**计费摘要、调用分类、任务/镜头、用户贡献、账本明细**。

## 2. OEM 后台调研结论（只读）

已登录并审查 `cms.richbest.cn/projects/`：

| OEM 层级 | 已看到的表达 | 应继承的原则 |
| --- | --- | --- |
| 项目列表 | 项目名称、所有者、技术信息、完成度、创建/更新时间、上帝视角 | 先回答“这是哪个项目、属于谁、现在什么状态” |
| 项目筛选 | 项目名称、手机号、用户名、邮箱 | 筛选维度与项目归属/负责人一致 |
| 项目详情 | `项目信息`、`分镜详情` 两个一级页签 | 概览与深度内容分层，避免列表塞进全部信息 |
| 项目内部 | 剧集 → 角色/场景/道具，分镜逐条展开 | 子对象按业务对象归类，并可继续定位 |

OEM 页面本身没有成本用量分类；本方案只复用其信息架构，不引入其“上帝视角”或编辑权限语义。

## 3. 当前系统基线与缺口

### 已有能力（复用，不重做）

- 所有面向用户的生成已要求或透传 `drama_id`；全能创作、AI 工具箱、主工作流均可归属项目。
- `billing_usage_logs` 与 `billing_transactions` 已保存 `drama_id`、`project_title_snapshot`、`source_kind`、`source_id`，用于历史名称稳定展示与审计。
- `/api/v1/admin/usage`、`/usage-summary` 已支持日期、用户、角色、分组、项目 ID 等过滤参数。
- 已有幂等的项目归属回填服务 `backfillProjectSnapshots`：仅回填可唯一安全归属的历史记录，歧义记录不动。
- 当前“模型用量”已有：总积分/调用/用户/项目/未关联项目卡片、按日趋势、用户→项目汇总、单条明细及分页。

### 当前缺口

1. 页面入口是“模型用量”，用户无法从“项目”开始查看成本。
2. 前端已定义 `filters.billing.drama_id` 和 `usageProjects`，但界面没有项目筛选器，已存在的 API 能力未被使用。
3. “用户→项目积分”把项目作为分组结果而非可进入的业务实体；项目名称、负责人、项目状态、创建/更新时间、调用构成均不可见。
4. 单条明细混合承担汇总、筛选和审计三件事，表格信息密度高但判断成本高。
5. `未关联项目（历史/全局）`只显示金额，未区分：历史待回填、确实全局操作、归属不明确，难以治理。

## 4. 信息架构（建议）

在运营后台“运营 / 计费”区域新增一级页签：

```text
项目用量管理
├─ 项目总览（默认）
│  └─ 项目详情抽屉 / 独立详情页
│     ├─ 概览
│     ├─ 调用构成
│     ├─ 工作流与镜头
│     ├─ 成员贡献
│     └─ 账本明细
├─ 未关联项目
│  ├─ 历史待归属（可安全回填 / 歧义，分开显示）
│  └─ 全局/无项目操作
└─ 原始用量明细（保留现有模型用量表）
```

“资金流水”保留为余额变动审计；“原始用量明细”保留为模型调用审计。项目用量管理只聚合**实际结算用量**，预授权/冻结单独展示，不能混入实际消费。

## 5. 页面与交互规格

### 5.1 项目总览

筛选区（默认近 30 天）：

- 时间：今天、近 7 天、近 30 天、自定义；统一按 `Asia/Shanghai` 展示。
- 项目名称（模糊搜索）、项目负责人（账号/显示名）、项目分组、项目状态。
- 调用类型（主工作流 / 全能创作 / AI 工具箱 / 图片 / 视频 / 后处理 / 语音）、模型。
- “含未关联项目”开关默认关闭，避免污染项目排行。

顶部指标：项目数、实际结算积分、冻结中积分、调用次数、活跃项目数、未关联积分（醒目但不混入项目总额）。

项目表字段：

| 分组 | 字段 | 说明 |
| --- | --- | --- |
| 项目身份 | 项目名称、项目 ID、负责人（显示名 + 账号）、项目分组 | 对齐 OEM 的项目信息/所有者表达 |
| 项目状态 | 项目状态、完成度、创建时间、最近活动时间 | 从 `dramas` / 项目工作流读取，不由账本推断 |
| 成本 | 实际结算积分、冻结中、调用次数、单次均值 | 实际与冻结必须分列 |
| 结构 | 主工作流、全能创作、AI 工具箱占比 | 以 `source_kind` 聚合 |
| 风险 | 待对账数、失败/可重试任务数、未归属记录数 | 仅展示可行动问题 |
| 操作 | 查看详情、查看明细、复制项目 ID | 无成本修改操作 |

默认按实际结算积分降序；支持按最近活动、调用次数、冻结中积分排序。项目行点击打开详情，不跳离当前筛选上下文。

### 5.2 项目详情

采用 OEM 的“概览 + 明细”的双层逻辑，建议抽屉宽度 `min(1180px, 94vw)`，桌面端高度内滚动，保证列表位置不丢失。

#### A. 概览

- 项目名称、ID、负责人、分组、状态、完成度、创建/更新时间。
- 本时间范围：实际结算、冻结中、调用次数、涉及模型数、待对账数。
- 与上一相同周期比较（无历史基线时显示 `—`，不得伪造同比）。
- 成本趋势：按日实际结算曲线；冻结作为虚线或独立标签，不相加。

#### B. 调用构成

- 一级：主工作流 / 全能创作 / AI 工具箱 / 其它。
- 二级：服务类型（文本、图片、视频、视频后处理、语音、认证）。
- 三级：模型、分辨率/时长/有无视频输入等计费条件。
- 每一行：调用次数、实际结算积分、冻结中、平均成本、最近调用时间。

#### C. 工作流与镜头

- 项目剧集 → 分镜/镜头（如有）→ 调用次数、实际结算、最后任务状态。
- 全能创作序列/镜头以 `source_kind` + `source_id` 映射；AI 工具箱显示工具运行名称和结果归属。
- 若记录来自旧版而无法定位子对象，显示“历史记录：仅可定位项目”，不猜测镜头。

#### D. 成员贡献

- 按用户显示：显示名、账号、角色、调用次数、实际结算、冻结、最近调用。
- 项目拥有者与实际执行人分开；管理员代操作也能被正确解释。

#### E. 账本明细

- 复用现有明细表，但预置当前 `drama_id`，并增加来源、关联对象、请求 ID、结算状态、价格快照摘要。
- 支持从明细返回项目详情；不可在这里直接改账。

### 5.3 未关联项目治理页

三类标签，不能统一叫“未关联项目”：

1. **可安全回填**：通过唯一且同一用户的关联任务可确定 `drama_id`；只展示预览、数量和预计影响项目数。
2. **归属歧义**：存在多个候选项目或缺少可靠关联；默认永不自动回填，需后续人工归因功能。
3. **全局/历史操作**：确无项目语义的旧记录或全局操作；保留事实，不强行塞入项目。

“执行安全回填”必须是独立受控操作：显示幂等键、候选数、可写入数、歧义数、影响项目数；二次确认；完成后生成审计记录。发布默认不自动回填任何历史数据。

## 6. 后端与数据方案

### 6.1 新接口

新增只读接口，均使用管理员鉴权：

```text
GET /api/v1/admin/project-usage
GET /api/v1/admin/project-usage/:dramaId
GET /api/v1/admin/project-usage/:dramaId/timeline
GET /api/v1/admin/project-usage/:dramaId/breakdown
GET /api/v1/admin/project-usage/:dramaId/workflows
GET /api/v1/admin/project-usage/:dramaId/members
GET /api/v1/admin/project-usage/unassigned
```

共同过滤参数：`date_from`、`date_to`、`tenant_id`、`owner_user_id`、`service_type`、`model`、`source_kind`、`status`、`keyword`、`page`、`page_size`。所有时间存取 UTC ISO、显示端显式格式化为 `Asia/Shanghai`。

### 6.2 聚合口径

- **实际结算**：`billing_usage_logs.charged_micro`；不从供应商响应或前端金额重算。
- **冻结中**：从仍有效的 `billing_authorizations` 独立聚合；不可写入 `charged_micro`。
- **项目名称**：详情页以当前 `dramas.title` 为主，同时返回 `project_title_snapshot` 作为历史审计字段。
- **归属**：以账本快照 `drama_id` 为主；禁止按当前用户“最近项目”推测历史归属。
- **来源分类**：统一标准化 `source_kind`（`video_generation`、`image_generation`、`omni_video`、`tool_run`、`text_generation`、`video_postprocess`、`tts` 等），未识别项返回 `other` 并保留原值。

### 6.3 查询与性能

- 复用已有 `idx_billing_usage_project_created (drama_id, created_at DESC)`；补充按常用组合的覆盖索引前先 `EXPLAIN QUERY PLAN`。
- 列表使用分页聚合，详情的子表分别分页；不在一个请求中返回全量账本。
- 各聚合在同一过滤快照下运行，避免列表/详情统计口径不一致。

## 7. 前端实施方案

1. 将现有“模型用量”拆为“项目用量管理”与“原始用量明细”两个页签；保留旧 URL/查询参数兼容。
2. 接入项目筛选下拉：使用新的项目列表 API，不再从当前页 `user_project_breakdown` 推导候选，避免只能筛到已出现在当前聚合结果里的项目。
3. 新建 `ProjectUsageTable`、`ProjectUsageDetail`、`UnassignedUsagePanel` 三个组件；`BillingTransactionTable` 继续复用。
4. 项目详情跨视图带上当前筛选参数；浏览器刷新或返回时保持 `tab`、`project_id`、日期范围。
5. 视觉上采用现有深色运营工作台基线，表格容器仅横向滚动，页面本身保持纵向可达；按 1280×720、1440×900、1920×1080 验收。

## 8. 发布与历史数据安全

| 数据范围 | 发布后行为 |
| --- | --- |
| 新建调用 | 沿用现有 `drama_id` 快照，无语义变化 |
| 已关联历史记录 | 只读纳入新项目视图 |
| 可唯一确认的未关联历史记录 | 默认不改；管理员显式确认后按幂等键回填 |
| 歧义/重复候选记录 | 明确排除自动回填，保留在治理页 |
| 全局操作 | 继续保持未关联，不伪造项目 |

回填复用 `backfillProjectSnapshots` 的幂等审计模式；需先在预发/备份副本做 dry-run，产出候选清单，确认后才允许生产执行。失败重试不得重复写账本、不得重复扣费、不得改变已完成媒体或任务状态。

## 9. 验收标准

1. 管理员可在 30 秒内完成“选时间 → 找项目 → 看该项目实际成本、冻结、调用构成、负责人”。
2. 选择项目后，概览、趋势、成员、工作流、账本明细的 `drama_id` 与筛选一致。
3. 实际结算与冻结绝不相加；单项目汇总等于该筛选下的项目明细之和（允许分页展示，但聚合必须完整）。
4. 新项目调用、全能创作、AI 工具箱、主工作流各至少一条测试数据均归入同一项目视图。
5. 未关联记录被清晰分为安全回填/歧义/全局，发布不自动修改历史数据。
6. 现有 `/usage`、`/usage-summary`、资金流水、价目表、审计接口保持向后兼容。
7. 后端新增聚合/权限/幂等回填测试；前端测试、生产构建及三个桌面视口实际浏览器验收均通过。

## 10. 需要审核的产品取舍

1. 一级入口命名：建议“项目用量管理”，而非“模型用量”。
2. 项目详情形态：建议先用右侧抽屉，后续当“工作流与镜头”信息增多再升级独立路由。
3. 默认时间范围：建议近 30 天；可在 URL 保持筛选状态。
4. 未关联项目：建议独立治理页，不在项目排行中混算。
5. 回填权限：建议仅平台运营管理员可执行，且必须输入二次确认文案并带幂等键。
