# 计费定价与结算改正方案

> 状态：待实施。本文只沉淀改正方案，不直接调整线上价目或账本余额。
>
> 基线：2026-08-11；范围：文本、视频、TTS、图片的价目展示、预授权、结算与审计。

## 1. 结论与边界

当前的主流程应继续保留：

```text
服务端报价并冻结上限
  → 服务端调用供应商
  → 有可核验实际用量则按预授权价格快照结算
  → 调用失败则释放
  → 成功但没有可核验用量则待对账，超时释放并记录平台损失
```

不应改为前端扣费、直接使用供应商 SDK、根据视频时长猜 token，或在供应商没有 usage 时直接扣用户。

“100 积分 = 1 元”是本平台的兑换规则，不是火山引擎的官方定价单位。火山官方价格应以人民币、SKU、计量单位和适用条件保存为成本依据；面向用户的积分价可以等于成本，也可以另行制定毛利规则，但两者必须可区分、可审计。

### 定价数据改正原则

1. `unit_size` 是价格的一部分，后台表格必须显示，例如“3000 积分 / 1,000,000 输出 token”。
2. 视频价必须随 `has_video_input`、`resolution`、`has_audio` 选择条件费率；没有匹配条件不得悄悄落到错误基础价。
3. 每个价目项保存 `vendor_price_cny`、来源 URL、核对日期、SKU/模型 ID、适用条件和“公开价/合同价”标志。
4. 如需毛利，不覆盖供应商成本价：增加单独的“用户销售积分价/倍率/服务费”版本。用户账本使用销售价，成本对账使用供应商价。
5. 无法确认同一 SKU 的价格应标为 `unverified`，生产调用前拒绝，或显式设为合同价并保留合同依据；不得以 0 积分放行。

## 3. 发现的结算问题与改正方案

| 优先级 | 问题 | 当前影响 | 改正方案 | 验收标准 |
| --- | --- | --- | --- | --- |
| P0 | 文本默认输出上限在供应商请求完成后才设为 8192 | 上游实际可输出超过冻结上限；结算被封顶，平台承担超额成本 | 在创建预授权前确定最终上限；同一上限写入供应商 `max_tokens`、预授权快照和日志。普通/流式文本共用一个函数 | 未传 `max_tokens` 的请求仍向供应商发送有限上限；实际用量大于上限时供应商侧不会生成超额输出。 |
| P0 | AI 工具重试复用原任务的预授权 | 已结算或已释放的任务重试可能不再冻结，形成免费重试 | 每次重试创建新的 `tool_run` 执行尝试、业务请求 ID 和预授权；原流水只关联原尝试 | 首次成功后重试产生第二笔 authorization 与第二笔 settlement；首次失败后重试也会重新冻结。 |
| P0 | 账本以整积分逐计量项四舍五入 | 小额真实成本被结算为 0 积分；文本常见 | 内部使用微积分（建议 `1 积分 = 10,000 微积分`）保存所有余额、冻结、流水、价格和快照；只在展示层转换为积分 | Lite 文本的小额 token 用量产生非零微积分；余额/冻结/流水守恒且历史数据换算前后一致。 |
| P1 | 图片请求可按 `count` 冻结，但供应商适配器固定 `n: 1`，完成时也只结算 1 张 | `count > 1` 时过度冻结，且语义不一致 | 在 API 层固定并校验 `count = 1`，或实现多图生成并按实际成功张数结算；二者只能选其一 | 传入 `count > 1` 被明确拒绝或返回并结算对应张数。 |
| P1 | 后台价目表未展示计量分母、价格条件、默认费率 | 管理员容易把 500 积分/万字符误读为每字符；视频可能误用默认价 | 价目表列改为“计量单位”“计量基数”“适用条件”“供应商成本价”“用户销售价”“来源/核对日” | TTS、文本、视频在页面上均可无歧义读出收费口径。 |
| P1 | 无 usage 的成功调用默认冻结 24 小时后释放 | 正确地避免猜测扣费，但会形成平台成本损失 | 按 SKU 定义对账策略：token 模型轮询用量；TTS 用 Unicode 字符本地结算；图片按成功张数；无可核验视频用量短期对账后释放并告警 | 每笔待对账记录有供应商请求 ID、原因、到期时间、平台损失审计；同用户同模型达到阈值继续限流。 |

## 4. 微积分迁移方案（P0）

当前字段名已使用 `*_micro`，但实际保存的是整积分。实施时将其语义统一为“微积分”，不改业务含义：

```text
1 积分 = 10,000 微积分
100 积分 = ¥1
```

迁移步骤：

1. 增加 `billing_unit_scale = 10000` 的运行时常量和数据库元数据版本，旧数据库未迁移时拒绝混合写入。
2. 在单个 SQLite 事务中，将余额、冻结、累计充值/消费、流水金额与余额快照、价目 `unit_price_micro`、条件费率、预授权快照和对账结果全部乘以 10,000。
3. 所有报价、冻结、结算和封顶计算都只使用微积分整数；继续使用 `BigInt` 做乘除和四舍五入。
4. API 同时返回 `*_micro`（精确值）与展示字段 `balance`、`frozen`、`charged`（最多两位或四位积分）；前端不得再把展示值回传用于账务写入。
5. 为迁移前后各准备一份固定账本样本，验证余额守恒、已结算流水不变、冻结总额不变、幂等重放不重复扣款。

不采用“每次最少扣 1 积分”作为默认修复，因为这会改变公开单价；若需要最低消费，应作为明确、可展示的平台服务费规则另行发布。

## 5. 实施顺序与测试

1. 先修 P0 文本上限与工具重试，并添加 HTTP 集成测试。
2. 再执行微积分迁移，先备份线上 SQLite，演练迁移和回滚；迁移成功后才启用真实小额扣费。
3. 修复图片 `count` 一致性，并完善后台价目表显示。
4. 为每个视频 SKU 补齐供应商响应样本和条件费率回归测试；未确认 SKU 不扩展生产调用。

必须新增或保留的验收用例：

- 余额不足时供应商请求不发出。
- 文本、视觉文本实际 `input_token` 与 `output_token` 均按预授权快照结算。
- 供应商 usage 超过上限时账本只扣冻结额，同时记录 `overage_micro`，且请求层已限制输出。
- 图片成功 1 张结算 1 张；失败释放；多张策略符合接口契约。
- TTS 以 Unicode 字符数冻结并结算。
- 视频有 usage 即结算；无 usage 创建待对账；到期后释放并产生审计记录。
- 同一请求 ID 重放不重复冻结或扣款；一次工具重试一定创建新的预授权。
- 微积分下 4,056 输入 token 的 Lite 调用不再被舍入为 0。

## 6. 本轮不做的事项

- 不改动现有公开价数值。
- 不将图片模型加入默认使用范围。
- 不绕过项目 HTTP API 直接调用供应商。
- 不把供应商返回缺失的 token 用量替换为猜测的“视频秒数费用”。
