# 20 人协作一致性与故障恢复测试

本报告记录下述代码基线的服务端故障测试。后续页面审计发现的离页、弹窗取消和旧版本提交问题，修复与验收见 [协作编辑回归](collaboration-edit-safety.md)。本报告中的“没有修改产品实现”仅指本次故障测试阶段。

## 目标和范围

按实际最多 20 人协作的规模，重点验证数据一致性和恢复能力。所有操作使用隔离数据库及临时用户，经项目 HTTP API 和 WebSocket 进入。没有真实供应商调用、费用或生产数据操作。产品代码基线为 `7d3228acabb78f076b537b2db374ac5cd021341e`。

本次只增加测试工具和报告。所有线上历史项目、任务、媒体与账本均排除，没有改动生产功能、数据库迁移或线上配置。

## 网络故障模型

客户端连接本地故障代理，再连接独立进程中的项目后端。HTTP 请求与响应各注入 20–149 ms 随机延迟；每个方向的 WebSocket 消息也使用同一延迟范围。每次采样有 2% 概率追加 1,000 ms 阻塞。固定随机种子为 20260910；线程调度和连接顺序仍可能影响具体时序。

WebSocket 在单条连接中保持消息顺序。代理不随意重排消息，也不将 TCP 上的 WebSocket 当作不可靠数据报。此次没有做操作系统级丢包、TCP 重传、带宽限制或公网线路测试。连接中断会丢弃尚未送达的缓冲消息，客户端依靠自己的文档与重连恢复。

部分场景每 5 秒随机断开 3 条连接。每 37 个写入确认，代理会在收到服务端结果后切断连接，不把该确认交给发起客户端。这用于验证“已保存但客户端不知道”的恢复路径。每 13 次更新额外重放一次相同请求，模拟应用层重复提交；这不是 TCP 产生重复消息。

## 测试场景

| 场景 | 用户 / 项目 / 文档 | 时长 | 故障与操作 |
| --- | --- | --- | --- |
| 同段文字并发 | 20 / 1 / 1 | 60 秒 | 所有人反复删除并插入段首重叠文字，随机延迟与阻塞 |
| 断线和重复提交 | 20 / 1 / 1 | 60 秒 | 同段冲突、反复断线、确认丢失、相同更新重放 |
| 跨项目与不同字段 | 20 / 4 / 8 | 60 秒 | 项目说明与分集剧本并行修改，含上述网络故障 |
| 写入中异常退出 | 20 / 1 / 1 | 60 秒 | 有写入尚未确认时强制终止后端两次，原数据库重新启动 |
| 持续网络故障 | 20 / 4 / 8 | 600 秒 | 持续并发冲突、随机延迟、断线、确认丢失和重复提交 |

客户端每秒产生一次修改。保存期间继续保留新输入，通过 generation 和 dirty 状态合并补发；每个客户端最多一个写请求等待确认。连接关闭后等待 1.5 秒重连。版本变化同时触发文本增量读取和项目详情 HTTP 刷新。

因此“生成的编辑次数”与“确认的写入批次数”不同。不能用二者的差额判断数据丢失。

## 一致性判据

每次本地产生修改时，将原始 Yjs 更新应用到独立参考文档。故障停止后，必须满足以下条件：

- 所有本地草稿均完成确认。
- 所有客户端文本、HTTP 协作文档和项目或分集业务字段，与参考文档逐字相同。
- 跨项目没有文本广播串入；非成员访问其他项目返回 404。
- 强制重启后，在禁止客户端重连和补发期间，通过 HTTP 检查已确认的插入与删除仍在持久化状态中。
- 没有非预期业务错误；注入故障产生的断线和失败请求单独计数。

独立参考文档仍使用相同的 Yjs 库。本测试验证项目保存、传输、补发和恢复流程，不是对 Yjs 算法的形式证明。同段并发修改可以得到交错文本；一致性通过不代表自动解决了作者意图之间的冲突。

## 复现

在 `backend-node` 目录执行：

```powershell
$env:COLLAB_RESILIENCE_OUTPUT = "$env:TEMP/collaboration-resilience-result.json"
node benchmarks/collaboration-resilience-test.js
```

默认四个 60 秒场景加一个 600 秒持续场景，另需初始化及恢复时间。快速检查可将 `COLLAB_RESILIENCE_SECONDS` 和 `COLLAB_RESILIENCE_SOAK_SECONDS` 都设为 `6`。随机种子由 `COLLAB_RESILIENCE_SEED` 指定。

测试工具不接受外部后端地址。它自行创建临时数据库与随机本地监听端口，完成后关闭进程并删除自己的临时数据。

## 结论的边界

这是 Node.js 客户端对项目 API 和协作保存流程的故障测试，没有启动 20 个真实浏览器。不覆盖输入法、页面渲染、浏览器关闭后未保存草稿、多个后端实例、机器断电或文件系统损坏。强制终止进程不等于机器断电。十分钟持续运行也不能证明数天或数周运行不会出现问题。

此次不以此前的 50 人延迟目标作为验收门槛。通过与否以已确认数据持久化、全部编辑收敛、故障结束后恢复和无非预期业务错误为依据。

## 2026-09-10 实测结果

Windows 本机，Node 24.21.0，AMD Ryzen 9 7940HX，系统可见内存约 15.2 GiB。测试后端与负载发生器使用独立进程。

| 场景 | 本地编辑次数 | 确认批次数 | 故障停止后核对耗时 | 结果 |
| --- | --- | --- | --- | --- |
| 同段文字与随机延迟 | 1,200 | 958 | 1.44 秒 | 通过 |
| 断线、确认丢失与重复提交 | 1,200 | 860 | 3.76 秒 | 通过 |
| 四项目八文档并行 | 1,200 | 1,115 | 1.46 秒 | 通过 |
| 写入中强制重启两次 | 1,200 | 1,139 | 1.05 秒 | 通过 |
| 10 分钟持续网络故障 | 12,000 | 11,149 | 0.88 秒 | 通过 |

上述四组没有非预期业务错误，全部编辑收敛。断线组注入 33 次主动断线、23 次确认丢失及 68 次重复更新；跨项目组分别注入 33、31、89 次。跨项目广播串入为 0，非成员读取返回 404。

异常重启的两次检查均有 20 个客户端写请求尚未确认。客户端重新连接前，已确认数据的持久化检查通过。这里确认的是“请求尚未确认时终止进程”，没有将强制退出精确定位到 SQLite 事务内部某条指令。

五组共 16,800 次本地修改，最终参考文档、全部客户端及数据库业务字段一致，所有草稿完成确认。共注入 423 次主动断线、365 次确认丢失、1,042 次重复更新，以及 5,018 次额外延迟阻塞。非预期业务错误和跨项目文本串入均为 0。

持续组单独注入了 357 次主动断线、311 次确认丢失、885 次重复更新。其 921 次传输失败来自故障过程，已经与非预期错误分开统计，不是“零请求失败”。网络恢复后仍能收敛，是本组的通过依据。

持续组后端平均 CPU 约占一个逻辑核的 32%，事件循环延迟 P99 为 50 ms。峰值 RSS 为 287 MiB，结束时为 230 MiB；每分钟采样没有显示持续内存上涨。故障期间活跃连接会暂时降至 18–19 条，恢复核对要求所有 20 个客户端重新可用。

本次没有发现数据一致性或服务恢复缺陷，因此没有修改产品实现。结论仅适用于上述故障模型和时长。
