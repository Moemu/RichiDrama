# 多人协作负载测试

20 人随机网络故障、同段冲突、多项目及异常重启的后续测试见 [一致性与故障恢复报告](collaboration-resilience-test.md)。本文保留最初的容量负载结果。

本测试使用独立后端进程和 Node.js 客户端。客户端经过项目 HTTP 登录，使用会话 Cookie 建立 WebSocket。每次请求携带独立请求 ID。

每组用户共同编辑同一个项目的 description。初始文本约 5,000 字，每个用户每秒替换一次自己的编号标记。修改同时包含删除和插入。客户端收到项目版本变化后，执行文本增量读取和项目详情 HTTP 刷新，与当前协作页面的主要通信路径一致。

每个客户端同时最多发送一个未确认写请求。若上一请求未确认，记录跳过次数，不用降低实际发出量掩盖负载不足。记录保存确认、全员可见、详情刷新、客户端调度延迟、接收字节和后端 CPU、内存及事件循环延迟。

持续写入结束后，将所有客户端、HTTP 项目详情和持久化协作文档逐字比较。同时检查每名用户的最新标记仅出现一次。随后全员断线，各自修改一次，等待 1.5 秒后集中重连并补发。最后重启后端，使用原会话重连，再次核对全部内容。此处是正常关闭后的重启，不是写入中强制杀进程。

## 隔离和兼容范围

脚本自行创建临时 SQLite 数据库，使用 WAL 和 5 秒 busy timeout。后端只监听随机本地端口，不接受外部服务地址。HTTP 白名单仅允许登录、创建测试项目、添加成员、读取项目和读取协作文档；不启动后台生成工作器，也不配置供应商。没有真实生成、扣费或生产数据操作。

只创建隔离测试记录。线上历史项目、任务、媒体和账本全部排除。此次仅新增测试工具与报告，没有修改产品逻辑、API 合约或数据库迁移。

## 复现

在 `backend-node` 目录执行：

```powershell
node benchmarks/collaboration-load-test.js
```

默认分别运行 10、30、50 人，每组持续 60 秒。JSON 输出到当前目录的 `collaboration-load-result.json`。

```powershell
$env:COLLAB_LOAD_USERS = '50'
$env:COLLAB_LOAD_SECONDS = '180'
$env:COLLAB_LOAD_OUTPUT = "$env:TEMP/collaboration-load-soak.json"
node benchmarks/collaboration-load-test.js
```

## 解释边界

这是本机单后端、单热点文档的通信负载测试。没有启动 50 个真实浏览器，因此不测 Vue 渲染、输入法、浏览器内存或画布布局。项目没有分集和分镜，详情刷新比大型实际项目轻。结果不涵盖公网延迟、Nginx、TLS、多人媒体处理、真实生成、多个后端实例或长时间运行。

接收流量是客户端收到的应用消息字节总量，不含 TCP、WebSocket 帧及 HTTP 刷新流量。单核 CPU 100% 表示占满一个逻辑核。SQLite 使用同一后端进程的同步连接，负载可能表现为事件循环排队；没有 SQLITE_BUSY 不能证明不存在数据库瓶颈。

本次观察目标为保存 P95 小于 500 毫秒、全员可见 P95 小于 1 秒，且无错误、无跳过、无内容不一致。这是本次基准目标，不是线上 SLA 或容量承诺。

## 2026-09-10 实测

产品代码基线：`7d3228acabb78f076b537b2db374ac5cd021341e`。Windows 本机，Node 24.21.0，AMD Ryzen 9 7940HX，32 个逻辑核，系统可见内存 15.2 GiB。负载发生器与后端使用不同进程，但共享同一台机器。

| 同时编辑人数 | 持续时间 | 目标 / 实际确认次数 | 保存 P95 | 全员同步 P95 | 详情刷新 P95 | 后端单核 CPU | 结果 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 10 | 60 秒 | 600 / 600 | 8 ms | 12 ms | 31 ms | 14% | 达到目标 |
| 30 | 60 秒 | 1,800 / 1,800 | 66 ms | 84 ms | 219 ms | 78% | 达到目标 |
| 50 | 60 秒 | 3,000 / 1,558 | 1,956 ms | 1,995 ms | 1,961 ms | 103% | 未达到目标 |
| 30 | 180 秒 | 5,400 / 5,400 | 122 ms | 143 ms | 347 ms | 86% | 达到目标 |

三组已发送的修改均收到确认，全部客户端与数据库内容一致；离线修改补发和正常重启恢复也通过。未出现请求错误或 SQLITE_BUSY/SQLITE_LOCKED。

50 人组受单个未确认请求限制，1,442 次计划输入未发出。因此实际吞吐只有每秒约 26 次，不能按每秒 50 次写入通过验收。跳过的计划输入不属于已经发送后丢失的数据。实际前端会继续接收本地输入并合并补发；本工具记录的是固定频率、每次单独确认的可达吞吐，不模拟所有键盘事件。

接收协作消息总量分别为 218、2,035、3,035 MiB。50 人组后端事件循环 P99 为 2,215 ms；客户端调度延迟 P99 为 47 ms。后端明显排队，客户端负载也较高，因此这组数据不能用于精确推断后端的绝对极限。

集中重连并同步离线内容耗时分别为 207、1,131、2,342 ms。正常重启并同步耗时分别为 794、1,109、1,874 ms。这些时间不含预先安排的 1.5 秒离线等待，不代表生产故障恢复时间。

追加的 30 人、180 秒测试没有错误、跳过或内容不一致。离线补发与重启恢复通过。后端峰值 RSS 为 318 MiB，接收流量共 6,145 MiB。保存 P99 为 195 ms，详情刷新最大耗时为 1,616 ms；说明仍存在刷新长尾。三分钟仅是短时持续负载检查，不能据此排除长期内存增长。

原始指标：[10/30/50 人组](benchmarks/collaboration-load-2026-09-10.json)、[30 人持续组](benchmarks/collaboration-load-soak-2026-09-10.json)。JSON 时间按 UTC 保存，测试在北京时间 2026-09-10 下午完成。

脚本验证包括 2 人短测、三档负载与追加持续组。已有 `projectCollaboration.integration.test.js` 和 `projectResourceImport.integration.test.js` 共 2 项集成测试通过，覆盖权限、历史私有项目、持久化媒体、重复请求和重启恢复。没有前端改动，因此本次没有重复前端构建与 UI 验收。

消费者检索覆盖 `frontweb/src`、`backend-node/src`、`backend-node/test` 中的协作消息、状态向量和协作表引用，共 15 个文件。涉及前端协作 composable、路由、权限、项目操作、文本持久化、项目资源、任务及现有集成测试。本次不更改这些消费者。

### 已确认的开销来源

`projectCollaborationService.updateText()` 每次写入都会加载并保存整个 Y.Doc，返回完整状态和完整文本。`projectCollaborationSocket` 将这一结果广播给所有同项目连接，并为每个接收方重新鉴权。用户数和写入次数同时增长时，广播量快速增加。

每 750 ms 的版本通知还会触发客户端文本读取和项目详情刷新。此次测试已包含这些请求；不能只用 WebSocket 握手成功来代表多人编辑能力。

建议下一步先减少每次更新的广播体积，再评估文档读写和重复刷新开销，并用相同负载复测。以上为优化方向，本次没有改变生产实现。当前证据不支持宣称“50 人同时高频编辑流畅”。
